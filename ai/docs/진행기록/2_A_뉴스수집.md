## 16. URL 기준 중복 제거 ✅ (2026-11-02)

- 코드: `hk_llm/dedup.py`
  - `url_key(url)`: 중복 판단용 주소. DB `article.url_key` 에 그대로 저장 (V5, `VARCHAR(500)`, UNIQUE)
  - `dedup_by_url(articles)`: 각 기사에 `url_key` 를 붙이고 같은 키는 **첫 건만** 남김
  - 이번 실행 안의 중복만 거름. 이미 DB 에 있는 기사는 18번에서 `uk_article_url_key` 로 걸러짐
- 확인: `python dedup.py` → `ok`

**`url_key` 만드는 규칙과 근거**

| 규칙 | 근거 |
|---|---|
| `utm_*`, `ref`, `input` 꼬리 뗌 | [../결정사항.md](../결정사항.md) 4번. 실제 사례: 연합 `?input=1195m`, 서경 `?ref=naver`, 이데일리 `utm_source=naver` ([../조사/뉴스소스_조사.md](../조사/뉴스소스_조사.md) 5번) |
| 기사 번호 꼬리(`newsId` 등)는 남김 | 같은 조사 5번: 이데일리는 `newsId` 가 기사 번호라 떼면 다른 기사가 같아짐 |
| 남은 꼬리는 이름순 정렬 | `?a=1&b=2` 와 `?b=2&a=1` 은 같은 주소 |
| 호스트만 소문자로 | 호스트는 대소문자 구분 없음, 경로는 구분할 수 있음 ([RFC 3986 6.2.2.1](https://www.rfc-editor.org/rfc/rfc3986#section-6.2.2.1)) |
| `#` 뒤는 뗌 | `#` 뒤는 서버로 가지 않음, 같은 문서 안 위치일 뿐 ([RFC 3986 3.5](https://www.rfc-editor.org/rfc/rfc3986#section-3.5)) |
| 끝의 `/` 뗌 | 언론사 기사 주소는 끝 `/` 유무로 다른 기사가 되지 않음 (가정, 문제 생기면 뺌) |
| 500자 넘으면 건너뛰고 로그 | `url_key VARCHAR(500)` (V5). 지금 RSS 주소는 최대 47자 |
| `http`↔`https`, `www.` 유무는 안 맞춤 | 아직 그런 사례를 못 봄 → 생기면 추가 |

## 18. 기사 목록 DB 저장 ✅ (2026-11-02)

- 코드: `hk_llm/service/collect_service.py` 의 `collect_rss()`
  - 흐름: `collect_run` 에 `RUNNING` 1줄 → RSS 8개 받기(15번) → 주소 중복 제거(16번) → `article` 에 `LISTED` 저장 → `collect_run` 을 `SUCCESS`/`FAILED` 로 마감
  - 저장은 이미 있던 `dao/article_dao.py` 의 `insert_listed()` 사용. `url_key` 가 이미 있으면 건너뜀 (`ON DUPLICATE KEY UPDATE`, V5 `uk_article_url_key`) → 30분마다 돌려도 새 기사만 들어감
  - `collect_run.collected_count` = **새로 저장된** 건수 (받은 건수 아님)

**실패 처리와 근거**

| 상황 | 처리 | 근거 |
|---|---|---|
| 피드 일부 실패 | `SUCCESS` + `error` 에 실패한 피드 주소 | 15번 `fetch_all()` 이 피드 하나 실패해도 나머지는 계속 받음. 받은 기사는 살림 |
| 피드 8개 전부 실패 | `FAILED` + 예외 다시 던짐 | 저장할 게 없음. 화면 "갱신 시각"(`collect_run`)이 성공으로 보이면 안 됨 |
| DB 저장 중 오류 | `FAILED` + `error` 에 원인 | 같은 이유 |

**확인** (2026-11-02 10:35~10:36 KST, 로컬 Docker MariaDB, 백엔드 Flyway V1~V6 적용 후)
- `python -m hk_llm.dao.article_dao` → `ok` (같은 `url_key` 두 번째는 0건, 시각 KST 왕복 일치)
- `python -m hk_llm.service.collect_service` → `ok`
  - 첫 실행: 받은 484건 → 주소 중복 제거 454건 → **새로 저장 454건**, 모두 `LISTED`
  - 바로 다시 실행: 받은 484건 → **새로 저장 0건**. `article` 줄 수 증가 = 돌려준 건수, `url_key` 중복 0
  - `collect_run`: 4번 실행 모두 `SUCCESS`, 실패 피드 0개

**고친 버그: 새 기사 수가 틀리게 셈**
- 증상: 두 번째 실행에서도 "새로 저장 454건" (`collect_run` run_id 2). DB 에는 중복이 안 들어감 → 건수만 틀림
- 원인: SQLAlchemy 가 PyMySQL 연결에 `CLIENT.FOUND_ROWS` 를 켬 → `ON DUPLICATE KEY UPDATE` 가 아무것도 안 바꿔도 rowcount 1 ([SQLAlchemy MySQL 문서 "Rowcount Support"](https://docs.sqlalchemy.org/en/20/dialects/mysql.html#rowcount-support))
- 수정: `article_dao.insert_listed()` 가 이미 있는 `url_key` 를 먼저 한 번에 조회하고 새 것만 INSERT. `ON DUPLICATE` 는 동시 실행 대비로 남김
- 시험도 강화: "2회차 ≤ 1회차" → "돌려준 건수 = 실제로 늘어난 줄 수"
- run_id 1~2 의 `collected_count` 는 버그 전 기록 (2번은 실제 0건)
