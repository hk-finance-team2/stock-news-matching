## 1-1. 가상환경 만들기 ✅

```bash
python -m venv .venv
```

- 위치: `ai/.venv` (레포 기준. 처음엔 로컬 `LLM 개발/.venv` 로 만듦)
- Antigravity 연결: `Ctrl+Shift+P` → `Python: Select Interpreter` → `.venv\Scripts\python.exe`
- 터미널 프롬프트 앞에 `(.venv)` 가 보이면 활성화된 것
- PowerShell 에서 활성화가 막히면 한 번만: `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`

## 1-6. 수집 대상 종목 범위 ✅ (2026-10-30)

**의논 과정**
1. 범위는 뉴스 소스에 따라 기준이 다름: 네이버 API 는 종목 수만큼 호출(일 25,000건 한도), RSS 는 종목 수와 무관
2. 선택지: A(API 메인) / B(RSS 메인) / C(둘 다) × 범위(전체 / 코스피200 / +코스닥150 / 데모용)
3. **결정: C + 코스피200** → 이후 1-7 에서 "API 는 과거 기록용" 으로 바뀜

참고: 네이버 API 일 25,000건 기준 (종목 1개 = 검색 1번)

| 범위 | 종목 수 | 30분마다 | 1시간마다 |
|---|---|---|---|
| 코스피200 | 200 | 9,600건/일 ✅ | 4,800건/일 ✅ |
| 코스피200 + 코스닥150 | 350 | 16,800건/일 ✅ | 8,400건/일 ✅ |
| 코스피 전체 | 829 | 39,792건/일 ❌ | 19,896건/일 ✅ |
| 전체 상장 | 2,762 | ❌ | 66,288건/일 ❌ |

**코스피200 목록 구하기**
- 선택지: ① KRX 에서 CSV 수동 다운로드 ② 다운로드 주소 자동 호출 ③ `pykrx`
- 확인: KRX 정보데이터시스템이 **KRX Data Marketplace 로 바뀌며 로그인 필수** → ②③ 은 로그인 처리가 필요
- **결정: ①** (구성종목은 매년 6월·12월에만 바뀜)
- 받는 법
  1. https://data.krx.co.kr 회원가입(무료) 후 로그인
  2. 통계 → 기본 통계 → 지수 → 주가지수 → **[11006] 지수구성종목** (메뉴 검색창에 "11006")
  3. 지수명 **코스피 200** → 조회일자 = 최근 거래일 → 조회
  4. 다운로드 아이콘 → **CSV**
  5. `hk_llm/data/kospi200.csv` 로 저장

**반영 결과**
- 201개 (200 + 분할 신설 종목 등 임시 편입 추정)
- 파일이 깨져 보인 이유: **CP949(EUC-KR) 인코딩** → UTF-8 편집기에서만 깨져 보임, 정상. 코드는 CP949 로 읽음

- 발견: KRX 약칭이 KIND 회사명과 다름 → 23번 매칭 별칭으로 활용

## 1-7. 수집 데이터 형식 정의 ✅ RSS 기준 (2026-10-30)

| # | 질문 | 결정 | 이유·근거 |

| 8 | 추가 정보 | 기자명만 | |

**7번 과정**
- "경제 기사 전부 요약 후 종목 연결" 비용 확인 → RSS 는 싸고, 비용 대부분은 네이버 API 쪽(하루 약 2만 건)
- 제안: "실시간은 RSS, 과거는 날짜 지정해서 네이버 API" → 확인 결과 **API 는 날짜 지정 불가, 최신 1,000건까지만** (조사 2번)
- 최종: **RSS(실시간) 와 API(과거 기록용) 분리**, API 는 주기·건수·예산 보류 → **RSS 실시간만 집중**

| 질문 | 결정 |

| DB | 로컬 MySQL, HeidiSQL 로 직접 생성 |

| 테이블 | 3개: `news_articles`, `news_article_stocks`, `news_pipeline_runs` → `hk_llm/schema.sql` (아래 업데이트에서 이름·방식 변경) |
| 본문 보관 | **7일 후 삭제, 요약은 계속 보관** (계속 보관 시 언론사 정책 충돌 우려) |
| 종목 테이블 | 안 만듦 — 종목 담당 팀원과 나중에 맞춤 |
| 버린 기사 | 줄은 남기고 상태만 표시 (지우면 다시 받아 다시 요약) |

**→ 업데이트: 팀 레포 규칙 확인 후 변경 (2026-10-30)**

GitHub `hk-finance-team2/stock-news-matching` 에 올리려다 팀 규칙(`AGENTS.md`, `docs/decisions.md`, `docs/db/schema.md`)과 부딪히는 점 발견

| 위에서 정한 것 | 팀 레포 규칙 | 처리 |
|---|---|---|
| 로컬 MySQL `hk_llm` | Docker MariaDB 11.8.9, `stocknews`, 포트 3308 | ⏸ 보류 |
| root 사용 | root 금지, 앱 전용 계정 | ⏸ 보류 |
| `schema.sql` 로 직접 생성 | 테이블은 **백엔드가 Flyway 로만** 생성. AI 테이블은 "컬럼 합의 후" | ✅ `schema.sql` 삭제 → [../AI테이블_제안.md](../AI테이블_제안.md) 로 제안 |
| 테이블 이름 `news_*`, 상태값 소문자 | 레포 `schema.md` 의 자리 이름 `article` 등, 값은 `role` 처럼 대문자 | ✅ `article`·`article_stock`·`collect_run`, 대문자 값으로 변경 |
| JSON 예시 snake_case, 시간대 없음 | camelCase + `+09:00` ISO-8601 | ✅ 예시 수정 |
| LLM 이 뽑은 회사명으로 매칭 | 요구사항의 매칭 점수 방식 (`match_setting`) | ⏸ 보류 (23번에서) |

- HeidiSQL 로 DB 만들기는 **하지 않음** (DB 방식 보류)
- 백엔드에 이미 `stock_info`, `stock_alias`(별칭) 테이블 있음 → 별칭 목록은 이걸 활용
