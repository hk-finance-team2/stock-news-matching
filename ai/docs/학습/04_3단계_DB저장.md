
- **Docker** = 프로그램을 "상자(컨테이너)"에 담아 누구 PC 에서나 똑같이 켜는 도구. 팀원 4명이 같은 DB 버전·설정을 쓰게 됨
- 설정은 레포 최상위 `docker-compose.yml`, 비밀번호는 `.env`
- **테이블은 누가 만드나?** 백엔드가 켜질 때 **Flyway** 가 `backend/src/main/resources/db/migration/V1~V6__*.sql` 을 순서대로 실행. AI 테이블은 `V5__create_ai_tables.sql`
  → 그래서 DB 를 처음 켠 PC 에서는 백엔드를 한 번 켜야 테이블이 생긴다

## `article` 테이블 주요 칸

| 칸 | 뜻 |
|---|---|
| `article_id` | 번호 (DB 가 자동으로 1, 2, 3 …) |
| `url_key` | 비교용 주소. **UNIQUE** = 같은 값 두 번 못 들어감 |
| `url`, `press`, `title`, `reporter`, `published_at` | 1단계에서 얻은 것 |

| `body` | 본문 (4단계, 7일 후 삭제) |
| `summary` | LLM 요약 (5단계, 계속 보관) |
| `retry_count`, `last_error` | 실패 횟수와 이유 |

## 코드 따라 읽기 (`save_listed`)

```python
have = set(conn.execute(EXISTS, {"keys": [a.url_key for a in articles]}).scalars())
new = [a for a in articles if a.url_key not in have]
for a in new:
    conn.execute(INSERT, params)
return len(new)
```
1. `EXISTS`: "이 `url_key` 들 중 DB 에 이미 있는 것" 을 **한 번에** 조회
2. 없는 것만 `new` 로 골라서 INSERT
3. 넣은 건수 돌려줌

### 오늘 잡은 버그 이야기 (2026-11-02)

처음엔 "INSERT 하고, DB 가 알려주는 **처리된 줄 수**를 더하기" 였다. 그런데 두 번째 실행에도 "새로 454건" 이 나왔다.
- 원인: 라이브러리(SQLAlchemy)가 DB 연결에 `FOUND_ROWS` 옵션을 켜 둠 → **이미 있어서 아무것도 안 바꾼 줄도 1로 셈**
- DB 에 중복이 들어간 건 아니었다 (UNIQUE 덕분). 숫자만 틀림 → 화면 "새 기사 수" 가 틀렸을 것
- 고침: "먼저 있는지 조회 → 없는 것만 넣기"
- 교훈: 시험이 "2회차 ≤ 1회차" 처럼 느슨하면 버그를 못 잡는다 → "돌려준 건수 = **실제로 늘어난 줄 수**" 로 강화

## `run.py`: 실행 기록 `collect_run`

```python
run_id = _run_start(conn)            # RUNNING 으로 1줄
... 1~3단계 ...
_run_finish(conn, run_id, "SUCCESS", new)   # 끝난 시각, 새 기사 수
```
- 화면의 **"마지막 갱신 시각"** 이 이 테이블에서 나온다
- 8개 피드가 **전부** 실패하거나 DB 저장이 실패하면 `FAILED` → 화면에 잘못된 갱신 시각이 안 뜸
- 일부 피드만 실패하면 `SUCCESS` + `error` 칸에 실패한 피드 주소

## 시간은 왜 `to_db` / `from_db` 를 거치나 (`db.py`)

DB 의 `DATETIME` 칸에는 **시간대 정보가 없다**. 파이썬은 `10:00+09:00` 처럼 시간대를 붙여서 다룬다.
→ 넣을 때: KST 로 맞추고 시간대 떼기 (`to_db`), 꺼낼 때: KST 다시 붙이기 (`from_db`)
