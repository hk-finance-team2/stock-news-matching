# V1 프로토타입 둘러보기

> 2026-11-10 첫 통합본(V1). 이 문서를 따라 **처음부터 끝까지 한 번 돌려 보고 코드를 따라가며 이해한 뒤**, 각자 개선할 것·화면(UI) 제안을 해 보는 것이 목표입니다 (11/10 회의).
> 정리: 김태경(백엔드1). 고칠 점이 보이면 PR 이나 Slack 으로 알려 주세요.

## 0. 한 줄로

뉴스·공시를 5분마다 모아 → AI 가 요약하고 어떤 종목 이야기인지·그 종목에 어떤 성격의 소식인지 판단해 근거 문장과 함께 저장하고 → 백엔드가 화면용으로 모아 → 화면이 보여 줍니다. **판단(투자)은 사용자가** 하고, 서비스는 **정보와 근거**만 줍니다.

## 1. V1 에 들어 있는 것 / 빠진 것

| 들어 있음 | 빠짐 (이유) |
|---|---|
| 언론사 7곳 RSS(증권·경제 섹션) + DART 주요 공시 수집, 5분마다 | **SNS(블로그·카페)**: 1차에서 뺌. 카페는 작성 날짜가 오지 않고, 블로그는 뉴스와 많이 겹치며, 기사 댓글·커뮤니티는 robots.txt 가 막음 (`decisions.md` 2026-11-09) |

| 회원가입·로그인, 관심 종목, 종목 토론 게시판 | |

## 2. 켜 보기

| 하고 싶은 것 | 명령 (레포 맨 위 폴더) | 화면 |
|---|---|---|
| 화면까지 한 번에 (데이터는 내 DB 에 있는 만큼) | `docker compose --profile full up -d --build` | http://localhost:5173 |
| 화면 코드를 고치며 보기 | `docker compose up -d --build` (DB + 백엔드) → `frontend` 폴더에서 `npm install` 후 `npm run dev` | http://localhost:5173 |
| API 만 보기 | `docker compose up -d --build` | http://localhost:8080/swagger-ui.html |

- 처음이면 [setup.md](setup.md) 1~4절(설치·`.env`)부터. 내 DB 에 기사가 없으면 setup.md 2절의 **데이터 파일·예시 기사**로 채웁니다
- `--profile ai`(AI 자동 수집)는 OpenAI 비용이 들어 **데이터 담당 PC 만** 켭니다

## 3. 데이터가 흐르는 길 (코드를 따라가는 순서)

```
[수집] RSS 7곳 + DART ─→ [본문] 사이트별로 본문만 오려 냄 ─→ [AI] LLM 1번: 요약·회사·역할·감성·근거 번호·사실 종류
   ─→ [검사·연결] 종목 사전으로 종목코드, 규칙 검사, 근거 문장 확인 ─→ [묶기] 같은 소식 묶음
   ─→ [DB] article · article_stock ─→ [백엔드] 화면용 API (집계는 SQL) ─→ [화면] V7
```

| 단계 | 하는 일 | 코드 | DB |
|---|---|---|---|
| ① 수집 | 언론사 7곳 증권·경제 RSS 11개, DART 주요 공시. 5분마다 | `ai/hk_llm/loop.py` → `run.py` → `steps/step1_rss.py`, `step2_dedup.py`, `step3_save.py`, `dart.py` | `article` (status `LISTED`) |
| ② 본문 | robots.txt 확인 후 본문만 오려 냄(사진·표·광고 제외), 7일 뒤 본문 삭제 | `steps/step4_body.py`, `robots.py`, `core/press_policy.py` | `article.body` (`FETCHED`) |
| ③ AI | 기사 1건에 LLM 1번(gpt-5.4-nano). 본문 앞 3,000자 | `steps/step5_summary.py` (지시문 `PROMPT`) | `article.summary`·`companies` (`SUMMARIZED`) |
| ④ 검사·연결 | 회사 이름 → 종목코드(사전·별칭), 부고·시황·명단 기사 거르기, 근거 문장에 종목 이름 확인 | `steps/step6_match.py`, AI 금지 언론사는 `title_only.py` | `article_stock` (`DONE` / `NO_STOCK`) |
| ⑤ 묶기·요약 | 같은 종목·24시간·제목이 비슷하면 같은 소식으로 묶음. 1시간마다 종목 하루 요약 | `steps/step7_group.py`, `step8_daily.py` | `article_stock.group_article_id`, `stock_daily_summary` |
| ⑥ 백엔드 | 화면용 API. 이슈 순위·감성 비율·언급량은 SQL 로 집계 | `backend/.../article`, `stock`, `search`, `status`, `watchlist`, `board`, `user` (+ `mapper/*.xml`) | 읽기 (회원·관심·게시판은 쓰기) |
| ⑦ 화면 | 홈(글 목록·이슈 종목), 글 상세, 종목별 조회, 검색, 관심 종목, 토론 | `frontend/src/pages/DashboardPageV7.jsx`, `api/index.js`(API 부르기), `api/adapters.js`(응답 → 화면 모양), `hooks/useApi.js` | — |

- 테이블 구조: [db/schema.md](db/schema.md) · API 칸 하나하나: [api.md](api.md) · AI 파트 자세히: [ai/README.md](../ai/README.md)

## 4. 화면에서 보이는 것과 그 뜻 (정보만 제공)

| 화면 | 뜻 | API 칸 |
|---|---|---|
| **기사 내용: 긍정 / 부정 / 중립 / 판단 보류** | 주가 예측이 아니라 "기사 속 사실이 지금 주주에게 어떤 성격인가". 근거가 전망·소문뿐이면 판단 보류 | `stocks[].sentiment` (`null` = 판단 보류·판단 안 함) |
| **주인공 / 함께 언급** | 이 기사의 주인공 종목인가, 같이 나온 종목인가 (관련도 % 대신) | `stocks[].role` |
| 근거 문장 + **일어난 일 / 회사 계획 / 전망 / 소문** | 왜 이 종목인지 원문 한 문장과 그 문장의 사실 종류 | `stocks[].evidence`, `factType` |
| **주가 움직임 뒤 기사** | 제목이 특징주·급등처럼 주가가 이미 움직인 뒤 쓴 기사 → 이미 반영됐을 수 있음 | `priceMoveTitle` |
| **공시 · 자기주식 취득** + "목적·방식에 따라 해석이 달라지는 공시" | 공시 유형과, 연구상 반응이 갈리는 유형인지 | `disclosureType`, `contextDependent` |
| **글 n건 · 소식 m건** | 같은 소식을 여러 언론사가 쓴 것을 1건으로 센 수 | 이슈 `eventCount`, 요약 `sentimentByEvent` |

## 5. 왜 이렇게 만들었나 (면접·발표 때 나올 질문)

각 결정의 이유·측정·검토한 대안은 [decisions.md](decisions.md) 에 날짜순으로 있습니다. 자주 묻는 것만:

| 질문 | 짧은 답 | decisions.md |
|---|---|---|
| 왜 LLM 을 기사 1건에 1번만? | 요약·회사·감성·근거를 한 번에 → 비용 한 달 약 1.4만 원 | AI 파트 설계 |
| 왜 본문 앞 3,000자? | 기사 97% 가 3,000자 안, 근거 문장 100% 가 안에 있음, 줄이면 놓치는 종목이 늘고 늘리는 비용은 2% | (백엔드1 로컬 기록 14) |
| 왜 호재·악재라고 안 하나? | 시장은 기대치 대비로 반응하고 미리 반영되기도 함 → 기사만으로 주가 방향을 말할 수 없음. 판단은 사용자 | 2026-11-10 |
| 같은 기사가 여러 언론사에 나오면? | 같은 소식으로 묶어 1건으로도 셈 (연결의 46% 가 반복 보도) | 2026-11-09 같은 소식 묶기 |
| SNS 는? | 막혀 있거나(댓글) 날짜가 없거나(카페) 뉴스와 겹쳐서(블로그) 1차에서 뺌 | 2026-11-09 SNS |
| RAG 는 안 쓰나? | 기사 1건씩 판단하는 구조라 검색할 자료가 없음. 임베딩을 쓸 만한 같은 소식 묶기는 비교해 봤지만 이득이 우연 범위 | 2026-11-09 같은 소식 묶기 |

## 6. 둘러보며 해 볼 것 (각자)

1. **한 기사를 끝까지 따라가기:** 화면에서 기사 하나를 고르고 → 글 상세 API(`/api/articles/{id}`) 응답 → `article`·`article_stock` 줄 → AI 로그(`docker compose logs ai`)에서 그 기사가 어떻게 처리됐는지
2. **이상한 점 찾기:** 엉뚱한 종목 연결, 이상한 요약, 화면에서 이해 안 되는 말 → 기사 번호와 함께 Slack 에
3. **UI 제안:** 지금 화면(V7)을 직접 고치기보다 **새 파일(예: `DashboardPageV8.jsx`)이나 `test/…` 브랜치**에서 시안을 만들어 비교 (`App.jsx` 한 줄로 바꿔 볼 수 있음). 데이터는 `api/adapters.js` 가 주는 모양을 그대로 쓰면 됨
4. **개선 PR:** 브랜치 `feature/파트-기능` → PR. API·DB 를 바꾸면 `docs/` 도 같은 PR 에서 (AGENTS.md)

## 7. 알려진 한계

- 감성은 기사에 적힌 만큼만 판단 (증권가 기대치·선반영은 기사에 없으면 모름) → 그래서 "정보"로만 보여 줌
- 같은 소식 묶기 정확도 약 83% (6쌍 중 1쌍은 다른 소식이 섞임) → 숨기지 않고 정보로만
- 사실 종류(`factType`)는 11/10 이후 새로 분석한 기사부터 채워짐
- 데이터는 각 PC 의 DB 마다 다름 (AI 수집은 데이터 담당 PC 에서만)
