## 배운 것

- **N+1 문제:** 목록 1번 + 항목마다 1번씩 = N+1번 DB 왕복. 글 20개 → 21번. 글 페이지를 먼저 가져오고 그 글 번호들로 `IN` 한 번 더 → 항상 2번
- **JOIN vs EXISTS:** JOIN은 연결된 수만큼 줄이 불어남(글 1개가 종목 4개면 4줄) → 페이지·중복이 틀어짐. "있나?"만 물을 땐 `EXISTS`
- **서브쿼리는 N+1이 아님:** 줄마다 계산해도 DB 왕복은 1번. N+1의 문제는 "왕복"
- **GROUP BY 집계:** 이슈 순위는 종목별, 감성 비율은 감성별, 언급량은 시간 칸별로 묶어 `COUNT`. `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`로 한 묶음 안에서 뉴스·SNS 따로 세기
- **빈 칸 채우기:** `GROUP BY`는 0건인 칸을 안 줌 → 모든 칸을 먼저 0으로 만들고 SQL 결과만 덮어씀 (출석부)
- **% 합 100 (최대 나머지 방식):** 1:1:1을 반올림하면 99 → 소수점을 버리고 모자란 만큼 버린 소수점이 큰 칸부터 1씩
- **MyBatis vs JPA:** JPA는 메서드 이름 규칙표로 SQL을 자동 조립(AI가 아님). 집계는 결국 직접 써야 해서 집계가 중심인 우리는 MyBatis
- **Flyway 반복 지시서(R__):** 내용이 바뀌면 다시 실행. 예시 기사를 켜고 끌 수 있게 `db/sample`에 따로
- **자동 테스트:** "이 요청이면 이 응답"을 코드로. 테스트마다 트랜잭션 롤백(투명 필름)이라 PC마다 DB가 달라도 같은 결과. 일부러 코드를 망가뜨려 테스트가 잡는지 확인
- **CI(GitHub Actions):** PR·merge 때 GitHub 컴퓨터가 "PR + 최신 main" 상태로 테스트를 돌려 ✅/❌. 설정 파일 하나(`.github/workflows/`)
- **merge 충돌:** 두 브랜치가 같은 파일 같은 자리(`decisions.md` 맨 끝)를 고치면 Git이 사람에게 물음. 둘 다 필요하면 둘 다 남김
